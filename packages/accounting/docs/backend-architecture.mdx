# AIBOS ERP Backend Architecture Documentation

*A comprehensive guide to the enterprise-grade accounting backend that powers the AI-BOS ERP system*

## Executive Summary

The AIBOS ERP backend represents a modern, enterprise-grade accounting system built on event sourcing principles with comprehensive financial reporting capabilities. This documentation serves as both a technical reference and a business blueprint for understanding how our accounting engine processes transactions, maintains data integrity, and generates sophisticated financial intelligence.

### Key Architectural Principles

- **Event Sourcing**: Complete audit trail with immutable event history
- **Domain-Driven Design**: Business logic encapsulated in domain models
- **Multi-Currency Support**: Real-time FX conversion with automated rebalancing
- **Resilience Patterns**: Circuit breakers, retry mechanisms, and graceful degradation
- **Compliance Ready**: Built-in support for MFRS/IFRS standards and audit requirements

## Core Domain Models

### Account Domain Model

The `Account` domain model represents the fundamental building block of our chart of accounts system.

```typescript
export class Account {
  public readonly accountCode: string;
  public readonly accountName: string;
  public readonly accountType: AccountType;
  public readonly parentAccountCode?: string;
  public readonly tenantId: string;
  public readonly isActive: boolean;
  public readonly balance: number;
  public readonly specialAccountType: SpecialAccountType;
  public readonly postingAllowed: boolean;
  public readonly companionLinks?: {
    accumulatedDepreciationCode?: string;
    depreciationExpenseCode?: string;
    allowanceAccountCode?: string;
  };
}
```

**Key Features:**
- **Immutable Design**: Accounts are immutable value objects with validation
- **Special Account Types**: Support for contra-accounts, provisions, and control accounts
- **Companion Linking**: Automatic linking between asset and depreciation accounts
- **Balance Validation**: Enforces debit/credit polarity rules
- **Hierarchical Structure**: Parent-child relationships for account organization

### Journal Entry Domain Model

The `JournalEntry` aggregate root manages the complete lifecycle of accounting transactions.

```typescript
export class JournalEntry extends AggregateRoot {
  private entries: JournalEntryLine[] = [];
  private status: JournalEntryStatus = JournalEntryStatus.DRAFT;
  private reference: string = '';
  private description: string = '';
  private postedAt?: Date;
  private postedBy?: string;
}
```

**Business Rules:**
- **Double-Entry Validation**: Ensures debits equal credits
- **Status Management**: Draft → Approved → Posted → Reversed workflow
- **Audit Trail**: Complete history of who posted what and when
- **Reversal Support**: Automatic creation of reversing entries
- **Multi-Currency**: Handles FX conversion and rebalancing

### Data Contracts

Type-safe data contracts using Zod schemas for runtime validation.

```typescript
export const JournalEntry = z.object({
  id: Id.optional(),
  reference: z.string().max(64).optional(),
  description: z.string().max(512).optional(),
  postedBy: z.string().max(128),
  postingDate: z.string(), // ISO date
  tenantId: Id,
  lines: z
    .array(JournalEntryLine)
    .min(2)
    .refine(
      (lines) => {
        const sum = lines.reduce((accumulator, l) => accumulator + l.amount.amount, 0);
        return Math.abs(sum) < 1e-9; // balanced
      },
      { message: 'Journal entry must be balanced (sum = 0)' },
    ),
});
```

**Contract Benefits:**
- **Runtime Validation**: Automatic validation of incoming data
- **Type Safety**: Compile-time type checking with TypeScript
- **Documentation**: Self-documenting API contracts
- **Error Messages**: Clear validation error messages
- **Business Rules**: Embedded business logic in schemas

### Currency Validation

```typescript
// Validate balanced (original currency per line), then enforce again post-conversion
const sumDebit = command.entries.reduce((s, entry) => s + Number(entry.debitAmount || 0), 0);
const sumCredit = command.entries.reduce((s, entry) => s + Number(entry.creditAmount || 0), 0);
if (Math.round((sumDebit - sumCredit) * 100) !== 0) {
  throw new Error('Journal not balanced in original amounts (sum debits != sum credits)');
}
```

## Database Schema Design

### Core Tables

```sql
-- Accounts table with hierarchical structure
CREATE TABLE accounts (
  id UUID PRIMARY KEY,
  account_code VARCHAR(20) NOT NULL,
  account_name VARCHAR(128) NOT NULL,
  account_type VARCHAR(20) NOT NULL,
  parent_account_code VARCHAR(20),
  tenant_id UUID NOT NULL,
  balance DECIMAL(15,2) DEFAULT 0,
  is_active BOOLEAN DEFAULT true,
  special_account_type VARCHAR(50),
  posting_allowed BOOLEAN DEFAULT true,
  created_at TIMESTAMP DEFAULT NOW(),
  updated_at TIMESTAMP DEFAULT NOW(),
  UNIQUE(account_code, tenant_id)
);

-- Journal entries with multi-currency support
CREATE TABLE journal_entries (
  id UUID PRIMARY KEY,
  journal_entry_id VARCHAR(64) NOT NULL,
  tenant_id UUID NOT NULL,
  reference VARCHAR(64),
  description TEXT,
  status VARCHAR(20) DEFAULT 'DRAFT',
  posted_at TIMESTAMP,
  posted_by VARCHAR(128),
  base_currency VARCHAR(3) DEFAULT 'MYR',
  created_at TIMESTAMP DEFAULT NOW(),
  updated_at TIMESTAMP DEFAULT NOW()
);

-- Journal entry lines with FX tracking
CREATE TABLE journal_entry_lines (
  id UUID PRIMARY KEY,
  journal_entry_id UUID REFERENCES journal_entries(id),
  account_code VARCHAR(20) NOT NULL,
  debit_amount DECIMAL(15,2) DEFAULT 0,
  credit_amount DECIMAL(15,2) DEFAULT 0,
  currency VARCHAR(3) NOT NULL,
  fx_rate DECIMAL(10,6),
  fx_date DATE,
  functional_currency VARCHAR(3),
  functional_debit DECIMAL(15,2),
  functional_credit DECIMAL(15,2),
  description TEXT,
  created_at TIMESTAMP DEFAULT NOW()
);
```

### Event Store Tables

```sql
-- Event store for domain events
CREATE TABLE event_store (

  status VARCHAR(20) DEFAULT 'PENDING'
);
```

## Security and Compliance

### Row-Level Security (RLS)

Tenant isolation at the database level.

```sql
-- Enable RLS on all tables
ALTER TABLE accounts ENABLE ROW LEVEL SECURITY;
ALTER TABLE journal_entries ENABLE ROW LEVEL SECURITY;
ALTER TABLE journal_entry_lines ENABLE ROW LEVEL SECURITY;

-- Create policies for tenant isolation
CREATE POLICY tenant_isolation ON accounts
  FOR ALL TO application_role
  USING (tenant_id = current_setting('app.current_tenant_id')::UUID);

CREATE POLICY tenant_isolation ON journal_entries
  FOR ALL TO application_role
  USING (tenant_id = current_setting('app.current_tenant_id')::UUID);
```
